# PDF 转换耗时与 Token 开销优化方案

日期：2026-09-07

状态：方案记录，四项均待实施。当前仅新增本文档，不修改运行代码、配置或容器，不触发模型调用。

## 目标与边界

减少重复模型请求、无效升级和重复本地处理，同时保持 TEX/PDF 可用性、表格结构、源页顺序和数据可追溯性。

- TEX/PDF 优先；JSON 的语义补充失败不阻断文档生成。
- 保留原始字段 ID、标签、值、行列关系、源页码及已有坐标信息，支持后续人工核对和智能体分析。
- 不因单纯的印刷体或手写内容不确定、值差异、元数据问题或提示性的同行校验而升级整页识别。
- 不通过删掉内容、随意改写字段值或掩盖编译失败来降低开销。
- 不要求输出页数与源 PDF 严格相等，仍须保证内容完整和源页顺序。
- 本方案不调整当前识别 DPI、模型配置和并发数。

## 四项概览

| 项目 | 调整 | 主要收益 |
| --- | --- | --- |
| 1 | GPT-6 升级前先做本地 TEX 补齐与规范化 | 减少可用规则解决的问题所引发的付费升级 |
| 2 | 将可选语义命名从 PDF 必经流程分离，并复用结构映射 | 减少逐表重复命名和 PDF 等待 |
| 3 | 识别升级与后续优化共用每页付费修复额度 | 控制同页跨阶段重复修复的开销 |
| 4 | 复用有效编译结果，仅重查变化内容 | 减少本地编译耗时和 CPU 使用 |

## 1. 升级前执行本地补齐与规范化

### 当前问题

部分确定性的 TEX 修复在整份优化阶段执行，单页识别检查时尚未应用。某些已知宏缺失或可规范化的语法问题，可能先触发 GPT-6 整页重新识别，之后才进入本地修复阶段。

### 拟议调整

```text
Sol 首次识别
  -> 本地 TEX 补齐与规范化
  -> 结构检查、必要的单页编译
  -> 仍存在明确问题时才升级 GPT-6
  -> 对返回候选执行同样的本地处理与检查
  -> 保存可用版本及问题记录
```

复用现有优化器中适合单页处理的确定性规则，例如已知控制序列规范化、已知宏及依赖补齐。表格分隔、分组类错误只有在规则能明确判断且保持结构时才自动修复，不能笼统删除括号、换行或表格命令。

前后阶段必须调用同一套规则，重复执行后结果应保持不变，避免重复插入宏、依赖或再次改坏表格。缓存和产物应对应实际检查过的 TEX 版本，保留原始响应与修复记录。

### 与原优化的关系

这是把一部分本地处理提前复用，不是提前运行整个优化器。整份布局、全局字段映射、合并与最终编译仍保留。

### 验证

- 用真实失败样本验证已知宏缺失及可确定修复的语法问题能够通过本地处理解决。
- 检查字段 ID、值、表格行列关系和内容没有意外变化，并抽查 PDF 布局。
- 对不能确定修复的结构错误，确认仍进入问题处理流程。
- 对比付费升级次数及升级原因；不能把所有编译错误都认定为可省掉的升级。

## 2. 分离可选语义命名，复用表单结构映射

### 当前问题

当前逐表命名请求的缓存指纹包含页码、表格序号和实际填写值等信息。同一表单换了页码或批次数据，可能无法复用已有命名结果；不同 worker 的缓存也缺少统一复用。

### 拟议调整

转换时保留原始可追溯数据与稳定字段 ID，使用确定性的技术标识满足 TEX 包装和定位要求。把供智能体使用的语义别名作为可选补充，允许在 PDF 完成后或入库时单独执行，不让命名服务成为 PDF 发布的必经依赖。

应提供专门控制语义命名的设置，不能通过关闭全部 LLM 功能误关必要的语法修复。具体配置名称在实施时确定。

后续语义命名按表单结构自动复用：

- 使用表头、行标签、单位、字段类型、表格结构及章节语境构建缓存键。
- 排除不影响语义的页码、文档内序号和变化的填写值；对确实影响语义消歧的内容保留必要上下文，不能一律删除所有值。
- 将模型、提示词和输出结构版本纳入缓存，避免错误复用旧语义映射。
- 跨 worker 使用支持事务的共享缓存，并合并同时发生的相同命名请求；实施时可评估 SQLite。
- 语义别名与源字段 ID 分离，后续命名调整不改变原始字段身份及定位关系。
- 命名失败或暂未执行时记录状态，保留基础 JSON；不覆盖原始值、不阻断 TEX/PDF。

不建立需要人工维护的全量业务字段字典，而是自动积累已见表单的结构映射。跨页、跨文件复用时仍需保留语义上下文，避免形似而含义不同的表格被错误归类。

### 收益与限制

仅延后命名是转移开销，可缩短 PDF 等待，但不会自动降低整个生命周期的 token。真正降低总 token 需要按需命名、结构缓存命中及相同请求去重。

### 验证

- 关闭可选命名后仍能生成 TEX/PDF、基础 JSON 和定位映射。
- 相同表单换页码或填写值时复用语义映射；不同单位或语义上下文不能错误复用。
- 命名不可用时流程继续，并留下明确的待补充状态。
- 后续语义补充能够按稳定 ID 关联原始字段，不丢失标签、值和来源。

## 3. 统一每页付费修复额度

### 当前问题

识别阶段的单次 GPT-6 升级和后续优化器的模型修复分别管理次数，因此同一页仍可能在不同阶段累计多次付费修复。

### 拟议调整

首次识别之外，每个源页面最多一次付费修复机会。识别阶段已经使用 GPT-6 修复的页面，后续优化阶段不再追加同页的模型修复请求。额度需要持久化，重启与续跑不能重置次数。

本地规范化、宏补齐、布局处理和 XeLaTeX 编译不调用模型，不占此额度。可选语义命名属于独立任务，不应混入 TEX 修复额度。

涉及多页的整份修复必须先明确影响页面和额度归属，不能通过一次整份调用绕过单页上限。请求已发出但结果未知时，也应保留尝试记录，避免续跑重复付费；传输重试与修复尝试的计数规则需在实施时明确。

额度用完后仍允许本地处理，保留已有 TEX、最佳可用结果和问题记录。不能把无法编译的 PDF 标记为成功，JSON 补充失败也不能丢弃已有 TEX/PDF。

### 与第 1 项的区别

第 1 项决定“升级前先怎么修”，第 3 项决定“同一页最多付费修几次”。两者不冲突，本地修复不消耗付费修复额度。

### 验证与取舍

验证识别、优化和续跑共用计数，以及额度耗尽时产物和错误记录仍保存。此项能限制费用，但会减少进一步付费修复的机会，需要对比最终可用率，不能宣称它本身提高识别准确率。

## 4. 复用编译检查结果

### 当前问题

单页检查已经存在缓存。进一步优化应关注后续阶段能否复用有效结果，避免把现状误认为完全没有编译缓存。

### 拟议调整

以实际编译的规范化 TEX、有效导言区、宏及依赖、编译器和相关配置版本判断缓存是否有效。内容或依赖变化才使对应检查失效。

例如只修改 JSON 的语义别名且 TEX 未变时，无需再次单独编译该页；如果命名操作实际改动了 TEX 宏或内容，则必须重新判断，不能只按业务操作名称跳过检查。

单页编译、表格测宽探针和整份编译的目标不同，不能相互冒充检查结果。只消除相同输入、相同检查目的下的重复编译，保留必要探针及最终整份 PDF 编译，包括必要的两遍 XeLaTeX。

### 收益与验证

编译是本地操作，不消耗模型 token，此项主要节省时间和 CPU。验证相同输入复用结果、页面及依赖变化正确失效，并确认最终合并布局、引用及源页顺序正常。

## 建议顺序与衡量方式

建议先实施第 1、2 项，再评估第 3 项对可用率的影响；第 4 项按实际编译耗时占比推进。本文档不代表任何一项已经启用。

使用同一组源页面和一致模型配置比较：

- 全流程输入、缓存输入及输出 token、估算费用，包含升级、修复和后续命名；缺失 usage 单独标记。
- GPT-6 升级次数、原因、本地规则修复成功数，以及跨阶段重复修复次数。
- 命名请求数、结构缓存命中率与待补充字段数量。
- 编译次数、缓存命中数、各阶段耗时及整份任务实际起止耗时。
- TEX/PDF 可用性、字段与内容完整性、表格布局和源页顺序。

并行模型请求耗时之和不等于整份任务耗时；识别结束后仍需执行的命名或入库补充也应纳入总成本。暂不承诺固定百分比的节省。

## 后续扩展，不属于上述四项

### 逐页优化流水线

识别完成一页后，执行本地修复、检查及可独立完成的页内优化并缓存；全部页面完成后，按源页码合并，统一处理公共宏、跨页关系、全局字段映射及最终编译。

流水线与第 1 项共用规范化规则。GPT-6 替换某页 TEX 后，必须使该页相关优化缓存失效。各模型阶段共用并发额度，避免阶段并发相加引发限流。

流水线可让本地处理与模型等待重叠，减少识别后的集中处理时间，但不会自动减少 token；模型并发已经饱和时，也不能保证显著提速。

### 较低成本模型的候选用途

GLM 等模型可优先评估语义命名、表单分类及后续 JSON 补充，这些结果独立保存，不覆盖原始字段值、不阻断 PDF。复杂表格视觉识别与结构修复需单独验证，不直接替换现有模型。

用户提到的“GLM3.5”具体 API 型号、视觉能力和价格尚未确认，实施前需确认，并按包含失败重试的总成本比较。本方案不接入或调用该模型。
